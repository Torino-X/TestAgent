# 自动审查与自动修复

每份生成的测试方案都附带一轮自动审查与可能的自动修复。本节解释审查什么、修复什么、哪些仍需人工处理。

## 一句话理解

**自动审查找问题，自动修复尝试解决问题，剩余问题交回给测试人员。**

## 自动审查检查什么？

### 1. 结构完整性

- 模板的必填章节是否齐全。
- 章节层级是否符合模板（一级、二级标题关系正确）。
- 关键字段（如编号、责任人）是否填写。

如果模板定义了"必须有 5 个章节"，但 AI 只生成了 3 个，审查会标出"缺少章节"。

### 2. 内部一致性

- **范围 ↔ 内容**：测试范围声明要测的功能，是否都出现在功能测试分析中？
- **规则 ↔ 测试点**：需求中的业务规则，是否都有对应的测试点？
- **角色 ↔ 权限**：需求中定义的角色，是否都出现在测试设计中？
- **字段 ↔ 测试数据**：核心字段是否都有测试数据示例？

例如，"范围"中提到"接口鉴权"，但"功能测试分析"中没有接口鉴权相关章节，审查会提示"功能测试分析与范围不一致"。

### 3. 明显缺漏

- **边界条件缺失**：是否覆盖必填、长度、唯一性、并发？
- **异常路径缺失**：是否覆盖网络中断、重复提交、超时？
- **安全相关缺失**：是否覆盖权限、加密、敏感字段？

这是基于通用测试经验的模式检查，不替代业务判断。

### 4. 风险与依赖

- 是否列出与外部系统的依赖。
- 是否识别数据准备依赖。
- 是否标出潜在阻塞项。

## 自动修复能做什么？

### 能修复

- 章节补全（自动补充缺失章节）。
- 内部不一致（调整描述以对齐）。
- 明显缺漏（追加通用测试点）。
- 简单的格式与编号问题。

### 不能修复

- 业务规则的"漏写"——如果需求里没有写，AI 不会替你猜。
- 风险等级排序——需要团队经验。
- 测试数据真实性——只能给出占位示例。
- 跨方案一致性——AI 不掌握其他项目的细节。

## 修复流程

```
生成章节 ──► 审查 ──► 通过？ ──► 完成
                          │
                          ▼ 否
                       修复一轮 ──► 再审查 ──► 通过？ ──► 完成
                                              │
                                              ▼ 否
                                          标记高风险 ──► 人工处理
```

## 阅读自动审查结论

任务完成后，"任务完成卡片"会显示审查结论，建议按以下顺序阅读：

### 第 1 步：看高风险章节

自动审查会用红/黄/绿三级标识每章风险：

| 颜色 | 含义 | 建议处理 |
| --- | --- | --- |
| 绿色 | 审查通过 | 可信度高，但仍建议人工抽检 |
| 黄色 | 存在可疑点 | 重点人工复核 |
| 红色 | 高风险 | 必须人工处理后再使用 |

### 第 2 步：看自动修复的章节

自动修复会在审查意见中列出，标明"修复了什么"。可以：

- 直接接受修复结果。
- 如果觉得修复方向不对，通过【修改章节】重新调整。

### 第 3 步：看人工复核清单

审查意见会列出"建议人工复核的事项"，例如：

- 风险等级评估是否合理。
- 测试数据是否需要替换为真实数据。
- 与历史方案的引用关系是否对齐。

## 与"格式丢失确认"的关系

自动审查和格式丢失确认是两个独立的步骤：

- **自动审查**：聚焦"内容质量"，由自动审查 + 自动修复处理。
- **格式丢失确认**：聚焦"导出排版"，由用户在导出阶段决定是否接受。

两者不会互相影响，也不会因为内容好就跳过格式检查，反之亦然。

## 何时需要跳过自动审查？

正常情况下不建议跳过自动审查。但如果：

- 模板非常简单（仅一两个章节）。
- 只是占位草稿，不打算评审。
- 修改单个章节的增量操作。

自动审查的"覆盖度"自然降低，但仍会做基础的结构检查。

## 进一步提升质量

如果你发现自动审查结论不够准确：

- **需求文档写得更结构化**：见[推荐需求文档结构](/help/article/recommended-requirement-structure)。
- **模板设计得更清晰**：见[如何设计适合 TestAgent 的模板](/help/article/template-design)。
- **绑定知识库**：让 AI 参考团队历史项目与规范。
