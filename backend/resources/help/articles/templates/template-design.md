# 如何设计适合 TestAgent 的模板

模板质量直接决定生成质量。本节给出设计模板的具体方法，帮助你做出既符合团队规范、又能让 AI 准确识别的模板。

## 核心原则

设计模板时始终问自己三个问题：

1. **AI 能识别吗？** 章节是否用 Word 标题样式定义？层级是否清晰？
2. **AI 知道写什么吗？** 章节标题是否表达了明确的语义？
3. **团队能用吗？** 模板是否与团队既有规范一致？

## 一、标题层级

### 推荐做法

- 使用 Word 内置的**标题样式**：标题 1、标题 2、标题 3。
- 一级标题数量建议 5–12 个。
- 二级标题用于一级章节内的分组。
- 三级及以下慎重使用，层级越深越难识别。

### 避免做法

- ❌ 只靠**字号**区分层级——一旦字号被统一修改，结构就丢失了。
- ❌ 只靠**加粗**或颜色——同上。
- ❌ 用手工编号（"第一章""Section 1"）代替标题样式——AI 难以识别层级。
- ❌ 章节顺序错乱（例如三级标题嵌套在一级标题之前）。

## 二、章节命名

### 命名原则

- **职责单一**：一个章节只表达一件事。
- **语义明确**：看到名字就知道里面写什么。
- **一致性强**：同类章节用相同的命名模式。

### 推荐命名

| 场景 | 推荐章节名 |
| --- | --- |
| 范围 | 测试范围 / 范围说明 / 测试对象 |
| 策略 | 测试策略 / 测试方法 / 测试方法论 |
| 功能 | 功能测试分析 / 功能测试要点 |
| 接口 | 接口测试分析 / 接口测试要点 |
| 性能 | 性能测试要点 / 性能指标 |
| 安全 | 安全测试要点 / 安全风险评估 |
| 数据 | 测试数据设计 / 测试数据准备 |
| 风险 | 风险与依赖 / 风险评估 |
| 进度 | 测试进度 / 人员安排 / 时间表 |
| 环境 | 测试环境 / 环境配置 |

### 避免命名

- ❌ "其他""补充""待定""未命名"——没有上下文。
- ❌ "第一节""第二章"——纯数字编号。
- ❌ "测试相关说明"——含义模糊。
- ❌ "附录 A：术语表"——AI 难识别为独立章节。
- ❌ 章节名相似但实际不同——例如同时有"测试策略"和"测试方法论"。

## 三、固定内容 vs 待生成内容

模板中应清楚区分两类内容：

### 固定内容（保留原样）

- 封面（项目编号、版本、密级）。
- 文档说明（版本历史）。
- 术语与缩略词表。
- 引用规范。
- 审批签字栏。
- 组织级测试规范。

### 待生成内容（AI 重写）

- 测试范围。
- 测试策略。
- 功能测试分析。
- 接口测试分析。
- 性能/安全/兼容性测试要点。
- 测试数据设计。
- 风险与依赖。
- 测试进度与人员安排。

### 区分方法

- 固定内容用**普通段落**样式（默认正文样式）。
- 待生成内容用**标题样式**（标题 1 / 标题 2）。
- 固定内容可以保留真实数据（封面、版本），但应避免把旧项目的真实数据放在待生成内容里。

## 四、表格设计

### 表格使用原则

- **每个表格表达一件事**：范围表、风险表、进度表，分别独立。
- **表头写在第一行**：表头单元格不要合并。
- **避免跨页大表**：超过一屏的表会让导出变得困难。
- **避免嵌套表**：表里套表会增加识别难度。
- **避免连续合并单元格**：横向、纵向合并都尽量减少。

### 推荐表格类型

| 表格 | 用途 | 表头示例 |
| --- | --- | --- |
| 范围表 | 测试范围与排除项 | 功能模块、是否覆盖、说明 |
| 策略矩阵 | 测试策略选择 | 测试类型、覆盖目标、适用阶段 |
| 风险表 | 风险与缓解措施 | 风险项、等级、缓解措施、责任人 |
| 进度表 | 测试进度安排 | 阶段、起止时间、负责人、产物 |
| 接口清单 | 接口测试范围 | 接口名、协议、方法、覆盖度 |

## 五、占位内容

### 推荐做法

- 用简短填写提示放在章节开头，例如"【此处描述测试范围，包含功能模块、端到端场景、排除项】"。
- 提示要明确告诉 AI 该写什么。
- 占位不要过长，三行以内最好。

### 避免做法

- ❌ 把旧项目的真实内容留在模板里——AI 会把它当作上下文继续使用。
- ❌ 占位过长（半页文字）——AI 难以分辨"占位"和"内容"。
- ❌ 占位里写"参考 XX 项目"——AI 不一定能理解那个项目。

## 六、模板迭代建议

模板不是一次设计到位的，需要在使用中迭代：

### 第一次设计（最小可用）

- 3–5 个一级章节。
- 每个章节一个占位说明。
- 不需要复杂的表格。

### 第一次使用后

- 用真实需求跑一遍生成，看识别是否正确。
- 看自动审查是否指出模板问题。
- 调整章节命名、占位措辞。

### 团队推广前

- 在 3–5 个不同需求上跑过。
- 自动审查结论稳定。
- 输出排版与团队规范一致。

### 持续迭代

- 每季度或每半年评估一次模板。
- 当业务类型新增（例如"数据合规"），增加对应章节。
- 当团队规范变化（例如引入新工具），调整对应章节。

## 七、设计自检清单

发布模板前对照检查：

- [ ] 标题样式正确（一级 / 二级清晰可识别）。
- [ ] 一级标题数量 5–15 个，覆盖完整测试方案结构。
- [ ] 每个一级章节有简短的占位说明。
- [ ] 表格无嵌套、无大面积合并。
- [ ] 没有遗留的真实业务数据或截图。
- [ ] 命名符合团队约定，没有同义词并存。
- [ ] 在 2–3 个真实需求上跑过，结果符合预期。
